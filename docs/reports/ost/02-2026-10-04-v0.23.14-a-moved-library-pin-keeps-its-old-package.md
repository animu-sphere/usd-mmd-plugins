# A moved library pin keeps its old package

- Date: 2026-10-04
- Version exercised: `ost 0.23.14`, the published `x86_64-pc-windows-msvc`
  asset, on this workstation (`cy2026-windows-x86_64-py313-usd`), in the
  default `OST_HOME`; the repository's CI pins 0.23.13
- Occasion: MOT-O10's implementation (#40), which moved both shared-motion
  adapters' `usd-motion-plugins` pins from v0.5.0 to v0.5.2 and added a
  `motionSource` pin
  ([MOTION_CONTRACT.md §12.6](../../design/MOTION_CONTRACT.md#126-the-arm-chains-reference-rest))
- Prior report: [01](01-2026-09-24-v0.23.3-a-bundle-is-staged-in-its-source-tree.md);
  the ecosystem's series is `usd-vrm-plugins`', whose reports 44 and 45 are
  the runtime half of this finding
- Next ask target: the next `ost` release

## TL;DR

**When a digest-pinned library moves, `ost build` reuses the root tree, and
CMake keeps every cached package whose old version still satisfies the
request.**

1. **P1: a moved external-library pin does not invalidate the root tree.**
   The toolchain names the new digests. But `motionCore_DIR` and
   `motionUsd_DIR` stay at the v0.5.0 digests, because `find_package(motionCore
   0.5)` is satisfied by what is cached. The build then linked v0.5.0
   `motionCore` against v0.5.2 `motionSource` and failed with LNK2019 (§2).
   `motionUsd` was stale too, and nothing reported it: had the link not
   failed, the acceptance test would have run against the old package.
   `usd-vrm-plugins`' report 45 shows `ost build` already discards a root tree
   configured against another *runtime*. Library pins have no such marker
   (§3).
2. **P3: "conflicting artifact pins" names neither side.** Two manifests that
   pin the same digests under different version ranges are refused as
   conflicting, with no hint of which field differs (§4).

## 1. What was being done

`libs/mmdSkeletonAdapter` and `libs/mmdMotionAdapter` pin `usd-motion-plugins`
artifacts by target and digest. #40 replaced every v0.5.0 digest with v0.5.2's
from that release's `external-library-pins.json`. It added `motionSource`,
raised the skeleton adapter's `find_package(motionRetarget …)` and the
package config to 0.5.2, and left `mmdMotionAdapter`'s
`find_package(motionCore 0.5 …)` and the acceptance test's
`find_package(motionUsd 0.5 …)` as they were. Those requests were still
correct, since v0.5.2 satisfies both.

## 2. The stale packages, reproduced

The first hit was in the main checkout. To reproduce it, a fresh worktree
(`C:/dev/tmp/mmd-ost02`) was built at the parent of #40 (`6313e65`), then
checked out at #40's merge (`f99a95a`) and built again, with `ost build` both
times.

| | before (`6313e65`) | after (`f99a95a`) | toolchain after |
| --- | --- | --- | --- |
| `motionCore_DIR` | `f06fef79…` (0.5.0) | `f06fef79…` (0.5.0) | `1d2ac0bc…` (0.5.2) |
| `motionRetarget_DIR` | `d6f83599…` (0.5.0) | `cbb27345…` (0.5.2) | `cbb27345…` |
| `motionSource_DIR` | — | `c508c65f…` (0.5.2) | `c508c65f…` |
| `motionUsd_DIR` | `f1154553…` (0.5.0) | `f1154553…` (0.5.0) | `e57fa819…` (0.5.2) |

`ost build` exits 1, with `motionSource.lib(CanonicalConversion.cpp.obj)`
unable to resolve `ApplyBasisToPosition` and `ApplyBasisToRotation`. Those are
v0.5.2 `motionCore` symbols, and the link line names the v0.5.0
`motionCore.lib`.

Only the package whose version request was raised moved. CMake re-searches a
cached `<Package>_DIR` only when the package config there rejects the request.
`.strata/targets/<target>/toolchain.cmake` prepends the new digests to
`CMAKE_PREFIX_PATH`, which is right. But a search path is not consulted for a
package already found.

## 3. Why the runtime is caught and a library is not

The root tree's cache holds `OPENSTRATA_RUNTIME_DIGEST` and
`OPENSTRATA_RUNTIME_PREFIX`, and `ost build` discards a tree whose recorded
runtime differs (`usd-vrm-plugins` report 45, §3). No cache entry records an
external library's digest, so nothing compares the pins a tree was configured
with against the pins it is built with.

The ask: record each materialized external-library digest the toolchain
prepends, and on a mismatch either discard the root tree, as for the runtime,
or unset that library's `<Package>_DIR` before configuring. Report 45 §4
applies here too: `ost plugin build` and `ost library build` should do the
same for their own trees. Here the standalone adapter trees were configured
for the first time after the pin moved, so they were not exercised.

Two workarounds, both verified:

- Delete the root tree's `CMakeCache.txt` and run `ost build`. Every package
  resolves to the new digests, and `ost test` passes 44 of 44.
- Delete the stale `<Package>_DIR:PATH=` entries. Deleting the value line
  alone leaves its `//` comment line behind. The next configure then fails
  with "Parse error in cache file" and rewrites the cache, and the configure
  after that succeeds. So delete the comment line too.

Raising each adapter's own `find_package` request to 0.5.2 would also force
the search. But that encodes a pin in CMake to make up for a build-tree cache,
and this repository does not do it.

## 4. "Conflicting artifact pins" names neither side

Both manifests pin `motionCore`, because the skeleton adapter states its
closure. After the digests were replaced, `mmdMotionAdapter` briefly kept
`version: ">=0.5,<0.6"` while `mmdSkeletonAdapter` said `">=0.5.2,<0.6"`, with
identical digests and sources. `ost build` stopped before configuring:

```text
error[VALIDATION_FAILED]: conflicting artifact pins for library 'motionCore'
```

Reproduced in the worktree by reverting the one range. Refusing the pair is
defensible. But the message names neither manifest nor the field that
differs, and with identical digests the difference is not obvious. The ask:
name both declaring manifests and the differing field.

## 5. Asks

| Priority | Ask |
| --- | --- |
| P1 | Treat a changed external-library digest like a changed runtime: record it in the tree, and discard or unset on a mismatch, in `ost build`, `ost plugin build` and `ost library build` |
| P3 | Name both manifests and the differing field in "conflicting artifact pins" |
